【零、换设备：一键适配】

  新手机刷入 Aegis 模块后，把桌面（或仓库 tools/）的
  Aegis_一键适配.sh 用 MT 管理器以 Root 执行即可，全自动：
    探测分簇/频率/capacity → 按内核公式算权重 → 生成
    rules.yaml/config.yaml（仅大块作用注释）→ 备份旧配置(.bak.时间戳)
    → 覆盖 →
    重启守护 → 报告写到 /sdcard/Aegis_适配建议.txt
  本手册【一】是该脚本背后的手工流程，一般不用再走。

【一、移植到新处理器的标准流程】（手工 / 给任何 AI）

  1. 先跑桌面的 aegis_cpu_probe.sh（用法在脚本头注释里），拿到三样东西：
       ① 分簇数与每簇关联核心（policy 目录，通常 3 簇，老机器可能 4 簇）
       ② 每簇硬件最低/最高频率、全部可用频点
       ③ 每核 cpu_capacity（算力值，同簇各核相同）

  2. 算「集群算力感知」权重（rules.yaml → cluster_profiles，每簇一条）：
       r   = 本簇 capacity ÷ 最小簇 capacity
       权重 = 1.0 + √(r − 1)        （最小簇自身 r=1 → 权重 1.0）
     8Gen2 案例（capacity 266 / 811 / 1024）：
       小核 r=1.00 → 1.00
       中核 r=3.05 → 1 + √2.05 = 2.43
       超大核 r=3.85 → 1 + √2.85 = 2.69
     有几个 policy 就写几条，顺序必须与 policy 编号升序一致。
     写死后把 auto_capacity_weight 设为 false（显式固化，换 ROM 也不漂）。

  3. perf 是「归一化比例」，0 = 该簇硬件最低频，1 = 该簇最高频：
       实际频率 = 最低频 + perf × (最高频 − 最低频)
       perf = (目标频率 − 最低频) ÷ (最高频 − 最低频)
     想让某档落某个频率，就用上面公式反推 perf，四舍五入到 2 位小数。

  4. 其余参数与具体 SoC 无关，默认值通用，一般不用动。


【二、config.yaml · CLG 日常调度参数（v7 内核 + 4.6 定值）】
  四个模式各有一套：powersave 省电 / balance 标准 / performance 性能
  / fast 极速（fast 是锁满频，不要改）。

  ★4.6 起采样节拍与屏幕状态自适应（与守护自身功耗直接相关）：
      亮屏 100ms（保跟手，与手势起步的几十毫秒需求匹配）
      息屏 500ms（eBPF map 读取 / top-app 扫描 / 消息投递降到 1/5）
    调度线程的超时与采样同拍（亮 100ms / 息 500ms）。下面提到"几 tick"
    亮屏按 0.1 秒换算，息屏按 0.5 秒换算。

 ★v7 只有一条公式，没有状态机、没有交互态、没有驻留：

     target_perf = 簇真实 max_util × gain，再夹在 floor 与 ceil 之间

   gain 是一条随负载单调上升的连续直线：
     raw ≤ down_threshold → gain = low_load_gain    （静态/轻载深度压频）
     raw ≥ up_threshold   → gain = headroom_factor  （重载留帧余量）
     两阈值之间线性插值，全程无阶跃、无模式切换。

   升频默认要连续 up_rate_limit_ticks 拍确认（滤后台单拍毛刺）；
   免确认通道（仅"前台在忙"时成立，两条）：
     ① touch_jump：单拍负载跳升 ≥ spike_jump_threshold（真实手势起步）
     ② idle_onset：4.6 新增，频率仍贴在地板上、前台线程刚超闸门
        （轻应用第一次点按/滑动，不需要等 2 拍确认）
   两条通道到的是上面公式算出的、被增益压过的目标，不是拉满，所以轻 App
   的起步只会快速到达正确的低档（如 MT 慢滑 → 614MHz），不会过给。
   后台不忙、息屏（top-app 为空）时两条通道都不成立，不增加空转。

   降频对称：raw < down_fast_threshold 立即快速沉底；滞回带内按
   slow_down_scale 放缓下降防锯齿。负载一掉频率就回去，不需要驻留。

 ─ 频率边界类 ──────────────────────────────────────────────────────
  perf_floor   性能地板（最低允许到哪）
    0.0 = 允许每簇下探各自硬件最低频（最省电）。
    4.6 三档统一 0.0：性能档旧版的 0.10 静态底频已撤掉——纯静态时不再
    无谓停在 0.10 那一段频率上，需要响应时靠低门槛快升（见下）。
    调大：最低频率抬高，静态更费电但瞬时响应更"跟手"。
    推荐：省电/标准/性能 0.0（要手感优先可给性能档 0.05，不建议更高）；
    极速 1.0。
  perf_ceil    性能天花板（该模式允许达到的最高比例）
    省电压到 0.70（中核顶 ~2054MHz，高于酷安钉频流畅线 1920，游戏请
    走 FAS 不受此限）；标准/性能给 1.0 不封顶。
  perf_init    刚切到该模式/刚接管时的起步性能
    推荐（4.6 定值）：省电 0.22 / 标准 0.32 / 性能 0.45。
  background_ceiling  前台进程树整体空闲的拍额外封顶
    作用：桌面/信息流静止、无动画无渲染时，把 target 再压一段，不依赖
          任何驻留状态；前台一忙当拍解除。
    4.6 定值：省电 0.22 / 标准 0.28 / 性能 0.38。
    调小更省电；调的太小会让"正在显示但不动"的页面切换略慢。
  cluster_ceil  按簇独立封顶（policy 升序，向量长度 = 本机簇数）
    4.6 定值：省电 [0.70, 0.70, 0.60]（超大核单独压到 0.60）
             标准 [1.0, 1.0, 0.85]（超大核留 15% 余量，只在大负载才动）
             性能 [1.0, 1.0, 1.0]（不封顶）
    只压超大核就改末位；1/2/3/4 簇机型按向量长度自然映射，缺省位回退
    perf_ceil。刷入时 aegis_adapt.sh 会按本机簇数与超大核槽位自动生成。

 ─ 负载→频率映射（v7 核心）─────────────────────────────────────────
  up_threshold    增益曲线到达高端的负载线（≥它就给满 headroom 余量）
    调小 = 更早给余量、更激进；调大 = 中载不给余量、更省电。
    定值：省电 0.80 / 标准 0.80 / 性能 0.72（性能档低门槛快升）。
  down_threshold  增益曲线停在低端的负载线（≤它只给 low_load_gain）
    必须小于 up_threshold，两者之间是增益线性过渡的"中频滞回带"。
    定值：省电 0.50 / 标准 0.48 / 性能 0.42。
  low_load_gain   增益曲线低端 ★Aegis 的省电核心★
    作用：静态/轻载时目标性能 = 利用率 × 此增益。100ms 分辨率下 MIUI
          后台同步会单拍冲到高 util，不压会反复顶高频率。
    触摸起步走免确认通道，但目标仍乘这条增益，所以压低不卡。
    调小：静态更省电，小于 0.40 非触摸的前台重活（安装、JS 计算）会
          明显变慢；1.0 = 不压频。
    定值：省电 0.42（推荐下限 0.40）/ 标准 0.50 / 性能 0.62 / 极速 1.0。
  headroom_factor 增益曲线高端（重载余量系数，≥1）
    作用：raw ≥ up_threshold 时目标 = 利用率 × 此系数，多给的部分是
          帧级突发缓冲。v3 起从 1.15~1.30 收到 1.05~1.10：实测中载
          根本不需要放大，余量只留给真重载。
    定值：省电 1.05 / 标准 1.05 / 性能 1.10 / 极速 2.0。
    换算参考（8Gen2 中核 499~2803MHz，4.6 省电档定值）：
      util 0.20（空转）   × 0.42 → perf≈0.08 → 约 683MHz
      util 0.42（红果）   × 0.42 → perf≈0.18 → 约 900MHz（随后沉底）
      util 0.70（中载）   增益≈0.90 → perf≈0.63 → 约 1.95GHz（被 ceil 0.70 封顶）
      util 0.85（真重载） × 1.05 → 顶 cluster/perf ceil = 2054MHz

 ─ 免确认通道 ─────────────────────────────────────────────────────
  interact_fg_util   前台闸门：最忙的前台 App 线程（UI/RenderThread）
                     利用率达到多少算"前台在忙"。
    实测桌面静态前台线程只有 0.03~0.05，打字 0.15~0.25，滑动 0.4~1.0，
    视频硬解约 0.10~0.15（低于闸门，正好走压频路径看电视）。
    4.6 定值：省电/标准/性能 统一 0.18（比旧版 0.25 更低，配合
    fg onset 让轻应用第一拍就能升；同时仍高于视频硬解的 0.10~0.15，
    看剧不会被误判为交互）。推荐范围 0.15~0.35。
  spike_jump_threshold  负载跳升门槛：单 tick 内簇 util 跳升 ≥ 此值，
    且前台超闸门时，升频免确认、当拍到目标。
    4.6 定值：省电 0.42 / 标准 0.42 / 性能 0.32（比 4.3 的 0.50 更宽，
    因为 fg onset 已单独覆盖"轻起步"，这里主要滤信息流抖动）。
    调大：只有更剧烈的手势起步才直通，更省电、抗抖动；调小更跟手但
          自然抖动会频繁钉高档。
    注意：它只决定"要不要当拍到"，到多高完全由增益公式决定。
  fg onset（4.6 新增，无配置项，由代码固定）
    条件：前台最忙线程 ≥ interact_fg_util 且 当前簇 perf ≤ perf_floor。
    效果：轻应用从静态第一次滑动/点按当拍到达目标档；后台与息屏不触发。
    对应代码：src/scheduler/cpu_load_governor.rs 的 idle_onset。

 ─ 平滑与速度 ─────────────────────────────────────────────────────
  smoothing_up / smoothing_down   EMA 指数平滑系数（0~1）
    新旧性能的融合比例，越大越跟手但越跳，越小越平稳但越迟钝。
    定值：省电 0.55/0.45、标准 0.70/0.35、性能 0.85/0.22。
    推荐：up 0.50~0.85（性能档最大），down 0.20~0.45。

 ─ 升降频确认（防抖）──────────────────────────────────────────────
  up_rate_limit_ticks    连续几拍升频条件成立才真的升（免确认通道旁路它）。
    定值：省电/标准 2，性能 1。
  down_rate_limit_ticks  连续几拍目标低于当前才开始降（快速沉底旁路它）。
    定值：省电/标准 2，性能 4（性能档性格即缓降，但不是驻留粘滞）。

 ─ 滞回带与快速沉底 ───────────────────────────────────────────────
  slow_up_scale      滞回带内升频步长缩放，低 util 端用它防抖。
    定值：省电 0.15 / 标准 0.18 / 性能 0.20；过低会有迟滞。
  slow_down_scale    滞回带内降频步长缩放。
    信息流滑动时 util 在 0.5~0.9 间逐拍抖动，jump 一拍把频率顶上去后，
    若下降太慢会粘在高档 → 体感"空高"。调大降得快更省电。
    定值：省电/标准 0.55，性能 0.40（保留一点响应余量，仍远快于驻留）。
  down_fast_threshold  raw 低于它立即走"快速沉底"（跳过 down_rate_limit）。
    定值：省电 0.25 / 标准 0.08 / 性能 0.18。
    标准档 0.08 是 4.6.1 下调值：交互中途 util 短暂回落到 0.08~0.25 不再被
    打回最低频，消除频率锯齿与切换/通知栏掉帧；只在前台几乎完全空闲
    （util<0.08）才允许 4x 快降。调大更容易锯齿，调小沉底变慢、稍费电。
  down_fast_mult      快速沉底倍率，越大沉得越快。
    定值：省电 4.5 / 标准 4.0 / 性能 3.0。
  up_jump_threshold   非触摸路径上目标性能跳升超过它时大步升频的门槛，
    服务后台持续突发（非单拍毛刺）。推荐 0.35，一般不用动。

 ─ 点按抬频（4.6.1 新增，独立输入通道）────────────────────────────
  input_boost_ms   手指按下瞬间把各簇下限抬到 0.85 档并保持的毫秒数
    0 = 关闭；默认 150（仅 balance 段显式写出，省电/性能/极速继承默认）。
    链路：touch_monitor.rs 用 evdev 只读监听 /dev/input/event*，只认
          BTN_TOUCH 按下与 ABS_MT_TRACKING_ID>=0 → DaemonEvent::UserTouch
          → on_input_boost() 把 min/max 写成同一频率（0.85 档，再按
          cluster_ceil 夹紧）→ 窗口内每拍绕过 background_ceiling →
          窗口结束交回正常降频路径自然回落。
    它不属于上面的 CLG 采样/增益循环，只在亮屏、非 fas、CLG 已接管、
    且事件延迟 <200ms 时生效；静止/滚动驻留不受影响。
    三个限制：
      ① 改这个值要就地重写 config.yaml（cat > 文件，别用 sed -i）+ 息屏
         再亮屏一次；该字段随 CLG 配置只在屏幕状态/模式切换时重新应用。
      ② input tap（InputManager 注入）不产生 evdev，不触发抬频；只有真
         实触摸才抬频，自动化脚本测不到这条通道。
      ③ 触摸设备只在守护启动时枚举一次，热插拔/外接输入设备需重启守护。
    实测（MIX Fold 3 标准档）：Recents 点按到首帧 p50 239→123ms、顿挫
      9/10→0/10；下拉通知栏起手最坏帧 75→31ms；看小说翻页折算
      <0.03%/小时；连续滑动只刷新窗口不叠档，功耗与不开时同量级。

 ─ 息屏红线（运行时收敛，非 YAML 定值）────────────────────────────
  进入息屏（屏幕关闭）后，守护对当前模式配置再做一次上限收敛：
    perf_ceil ≤ 0.35、每簇 cluster_ceil ≤ 0.35
    background_ceiling ≤ 0.30
    smoothing_up = 0.15、smoothing_down = 1.0
    slow_up_scale ≤ 0.15、down_fast_threshold ≥ 0.30
  亮屏后恢复该模式原值。效果：后台同步/推送不再把大核顶到高频，负载一落
  立即沉底；8Gen2 中核≈1.3GHz、超大核≈1.5GHz 就是夜间上限。
  调夜间功耗只需改 src/scheduler/mod.rs 的 0.35 / 0.30 两个数字。


【三、rules.yaml · FAS 游戏帧感知调度参数】（仅 FAS 应用生效）

  fas_enabled   FAS 全局开关
    false（默认）= 普通应用零探针零空转；只有 app_modes 里标 "fas"
                  的游戏进前台才唤醒 FAS（推荐，最省电）。
    true = 全局模式为 fas 时所有应用都可走 FAS。
  global_mode   日常模式：powersave/balance/performance/fast/fas
  app_modes     每个包名单独指定模式（游戏填 "fas"）

  fas_rules:
    fps_gears        全局可选帧率档（游戏实际渲染帧率动态匹配）
    fps_margin       帧率余量，帧稳在"目标+余量"以下就降频省电（帧）
    per_app_profiles 每个游戏单独的 target_fps / fps_margin

    cluster_profiles / auto_capacity_weight
      三簇算力权重，算法见第一部分。8Gen2 定制：1.00 / 2.43 / 2.69。
      权重越大：低 perf 时该簇越被压低频（省电），高 perf 时仍能拉满。
      中核/超大核权重加大 → 轻载游戏更愿意用小核、更省电；
      调小 → 更早动用大核、更稳帧但更费电。建议 ±0.2 以内微调。

    PID 控制器（帧率反馈调性能的快慢/过冲）：
      kp 0.05  比例项，越大帧率掉时补得越猛（太大频率抖动）
      ki 0.01  积分项，消除长期偏差（太大过冲）
      kd 0.006 微分项，压制变化速度（太大反应迟钝）

    perf_floor / perf_init / perf_ceil（FAS 专用，按频率表换算）
      8Gen2 定制：floor 0.30（≈小820/中1190/超大1425，游戏起步不卡）
                 init 0.50（≈小1162/中1651/超大1978），ceil 1.0
      floor 调高：最低帧更稳但更费电；调低更省电但复杂场景可能掉帧。
    perf_cold_boot 0.85   游戏冷启动头几秒的性能（防加载卡）
    freq_hysteresis 0.015 频率迟滞（比例），小于此变化不下发，防抖动

    loading_perf_floor/ceiling 0.60/0.70   加载条场景锁定的性能区间
    post_loading_perf 0.65                 加载完后的保护性能
    downgrade_boost_perf_inc 0.18          降档后发现掉帧的紧急提频量
    fast_decay_*                           连续稳帧时的快速降频步长（省电）
    （这些帧计数类参数与 SoC 无关，保持默认即可，不用按处理器换算）

  注：FAS 只在"亮屏 + 前台模式为 fas"时激活，息屏与普通应用下探针完全
      卸载、零空转；4.6 的息屏 500ms 采样不影响 FAS（其内部按真实
      elapsed/Instant 计时，与 tick 无关）。


【四、8Gen2 / 领先版实测数据表】

  · 下表主体测于 v7 首版参数（headroom 1.15 / ceil 0.75 / jump 0.40）。

  钉频对照实验（大核封 864MHz 逼任务留在中核，GFX 量真实频率门槛）：
    酷安信息流滑动：p3=1171 明显卡（95分位28ms/99分位42ms）
                    p3=1401 卡（23/32ms），p3=1651 勉强（18/26ms）
                    p3=1920 流畅（17/23ms）← 省电档就按这条线给频

  v7 日用实测（省电档，酷安/红果自动匹配 powersave）：
    MT管理器静止     p3 中位 499（贴硬件底）
    MT管理器慢滑     p3 中位 499~614，≥1500 仅 3%，大核基本不动
                     （v6 交互态：中位 1171、常被踹到 2093/2726）
    酷安慢滑/快滑    p3 中位 1920（钉频实测流畅线），顶格 2188 仅 16%，
                     大核 ≥2GHz 仅 3%；GFX 0 丢帧、0 次错过 vsync、
                     95 分位 17ms（与 v6 原参持平）
    红果短剧播放     p3 中位 614（v6 为 1651），≤1171 占 78%，
                     ≥1500 由 72% 降到 16%；前台最忙线程仅 ~15%
    桌面静态         p3 贴 499~614
  结论：轻 App 的"空高"来自 v6 交互态把偶发前台抖动当触摸首拍拉满并驻留
        0.8 秒；v7 无状态公式 + 双免确认后，频率随真实负载即起即落。


【五、调参纪律（避免改坏）】
  · 一次只动 1~2 个参数，每个参数小幅调整（步长 0.05~0.10）后实测。
  · up_threshold 必须 > down_threshold；low_load_gain 范围 0.10~1.00，
    headroom_factor ≥ 1.0，gain 曲线才能保持单调不跳变。
  · 省电与流畅靠"低地板 + 连续增益曲线 + 免确认起步 + 快速沉底"
    四件事配合，不要抬 perf_floor 换流畅，也不要加驻留/状态补丁——
    那正是 v6 空高耗电的来源；4.6 的 fg onset 同样是"无状态单拍"，
    不是新的驻留。
  · 怀疑某场景给频不够：先钉频 + GFX 量出真实流畅线（见第四部分酷安
    实验），再反推该负载下的增益，不要凭感觉抬天花板。
  · 改息屏红线/采样节拍时，采样与调度超时必须同步改，并同步
    cpu_monitor.rs 的单测 sample_interval_follows_screen_state。
  · rules.yaml 改完约 3 秒热生效；config.yaml 不热加载，改完必须
    killall -9 Aegis 再重新拉起（或重启手机）。
  · fast 极速档锁满频，所有压空转调参只针对省电/标准/性能三档。


【六、charge_guard.conf · 充电阈值（v1.7）】

  charge_full        充满即停：1=开启。充到 100%（或低电流涓流）即停充。
  charge_full_latch  本次插电锁存（4.6 新增，默认 1）
    1 = 充满停充后，只要充电器还插着就绝不再因电量回落补电
        （100%→99% 不重新充）；只有物理拔电才解除，下次插电照常充满。
        判定插拔只读 power_supply 的 online（无则 present），不读
        battery status（主动停充后 status 本身就是 Not charging）。
        安全阀：电量跌到 power_start 以下自动解锁，避免永久不充电。
    0 = 旧行为（v1.6）：掉到 99% 立即补电回 100%（浮充，更耗电、更伤电池）。
  power_start        恢复充电电量：只有关闭充满即停时才参与恢复判定；
                     charge_full_latch=0 时也用于"低于此值恢复"的旧逻辑。
                     v1.7 锁存期间电量低于它 → 自动解除锁存（安全阀）。
  power_stop         普通停充阈值（未开充满即停时按此停充）。
  power_stop_time    到达阈值后延时几秒再停充（默认 3，开启充满即停后失效）。
  power_reset        自动拔插（个别机型激活快充用），默认关闭。
  预约充电 / 保底电量：保底补电为 +10% 滞回锁存（低于保底一路充到
                      floor+10 才停，不来回抖动）。

  日常建议：charge_full=1 + charge_full_latch=1（睡觉不拔电也不浮充）。
  验证：WebUI 显示"已锁存"或 status.kv 的 full_latch=1；拔线重插后应恢复
        充电；需要立即恢复可执行 charge_guardd restore（会清理锁存）。
