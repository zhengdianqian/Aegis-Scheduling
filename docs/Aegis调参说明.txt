【一、移植到新处理器的标准流程】（给任何 AI / 任何人）

  1. 先跑桌面的 aegis_cpu_probe.sh（用法在脚本头注释里），拿到三样东西：
       ① 分簇数与每簇关联核心（policy 目录，通常 3 簇，老机器可能 4 簇）
       ② 每簇硬件最低/最高频率、全部可用频点
       ③ 每核 cpu_capacity（算力值，同簇各核相同）

  2. 算「集群算力感知」权重（rules.yaml → cluster_profiles，每簇一条）：
       r   = 本簇 capacity ÷ 最小簇 capacity
       权重 = 1.0 + √(r − 1)        （最小簇自身 r=1 → 权重 1.0）
     8Gen2 案例（capacity 266 / 811 / 1024）：
       小核 r=1.00 → 1.00
       中核 r=3.05 → 1 + √2.05 = 2.43
       超大核 r=3.85 → 1 + √2.85 = 2.69
     有几个 policy 就写几条，顺序必须与 policy 编号升序一致。
     写死后把 auto_capacity_weight 设为 false（显式固化，换 ROM 也不漂）。

  3. perf 是「归一化比例」，0 = 该簇硬件最低频，1 = 该簇最高频：
       实际频率 = 最低频 + perf × (最高频 − 最低频)
       perf = (目标频率 − 最低频) ÷ (最高频 − 最低频)
     想让某档落某个频率，就用上面公式反推 perf，四舍五入到 2 位小数。

  4. 其余参数与具体 SoC 无关，默认值通用，一般不用动。


【二、config.yaml · CLG 日常调度参数】
  四个模式各有一套：powersave 省电 / balance 均衡 / performance 性能
  / fast 极速（fast 是锁满频，不要改）。
  tick（采样间隔）= 100ms，下面提到"几 tick"都按 0.1 秒换算。
  ★调度分两种状态：交互态（前台在触摸/渲染）与非交互态（静态/后台）。
    交互态里：利用率不压缩、余量给满、首拍一步升频到位、只允许匀速降频；
    非交互态：负载整体 ×low_load_gain 压缩、尖峰衰减、快速沉底。
    状态判定由下面的 interact_hold_ticks / interact_fg_util 两个参数控制。

 ─ 频率边界类 ──────────────────────────────────────────────────────
  perf_floor   性能地板（最低允许到哪）
    作用：目标性能再低也不会被压过这条线。
    0.0 = 允许每簇下探各自硬件最低频（最省电，推荐日用）。
    调大：最低频率抬高，静态更费电但瞬时响应更"跟手"（适合性能档）。
    推荐：省电/标准 0.0；性能 0.10 左右；极速 1.0。
  perf_ceil    性能天花板
    作用：该模式允许达到的最高比例。
    省电可压到 0.75 限最高频省电；标准/性能给 1.0 不封顶。
  perf_init    刚切到该模式/刚接管时的起步性能
    作用：决定切模式后头几百毫秒的频率，太小切模式瞬间会"闷一下"。
    推荐：省电 0.25 / 标准 0.35 / 性能 0.55。

 ─ 负载→频率映射 ───────────────────────────────────────────────────
  up_threshold    升频阈值（利用率高于它，判定需要升频）
    调小（如0.55）= 更激进、更早升频，流畅但费电；
    调大（如0.75）= 更晚升频，省电但可能觉得"肉"。
    推荐：省电 0.75 / 标准 0.70 / 性能 0.55。
  down_threshold  降频阈值（利用率低于它，判定可以降频）
    注意它必须小于 up_threshold，两者之间是"滞回带"（防止来回跳频）。
    推荐：省电 0.45 / 标准 0.40 / 性能 0.35。
  low_load_gain   非交互态负载压缩增益 ★Aegis 的省电核心★
    作用：非交互态下，目标性能 = 利用率 × 此增益（所有负载水平都压缩，
          不只低载——100ms 分辨率下后台任务会单拍冲到 0.7+，不压会反复
          顶高频率）。专门治"负载不高但频率悬在半空"（看小说/短视频中核
          卡在 1171 下不来、MIUI 后台同步乱拉频）。
    触摸滑动/惯性动画期间自动进入交互态，利用率走原值、不受它影响，
    所以压低了也不会卡。
    调小：静态频率更低更省电，太小（<0.4）非触摸的前台重活（安装、JS
          计算）会变慢；调大（1.0=关闭此功能）：完全跟随真实负载。
    推荐：省电 0.45 / 标准 0.55 / 性能 0.75 / 极速 1.0。
    换算参考（以8Gen2中核 499~2803MHz 为例）：
      非交互 util 0.30 × gain 0.55 → 目标约 700MHz（静态阅读档位）
      非交互 util 0.65 × gain 0.55 → 目标约 1240MHz（视频解码必要供给）

 ─ 交互识别（滑动防卡核心）────────────────────────────────────────
  interact_fg_util   前台闸门：最忙的前台 App 线程（UI/RenderThread）
                     利用率达到多少算"前台在忙"。
    作用：只有前台 App 自己在忙才可能进入交互态，后台同步/推送即使把
          整簇利用率冲到 0.8 也不给频。实测桌面静态前台线程只有 0.03~
          0.05，滑动时 0.24~0.48，视频硬解约 0.10~0.15（走压缩路径，
          正好符合"看电视低功耗"）。
    调小（如0.15）：更容易进交互态、更跟手，但视频等前台轻载也会给频
          费电；调大（如0.40）：更省电但慢滑开头可能有 1~2 拍迟滞。
    0 = 不校验前台（不推荐，后台噪声可触发交互态）。
    推荐 0.25，范围 0.15~0.35。
  interact_hold_ticks   交互驻留拍数（1 tick = 100ms）
    作用：进入交互态后保持多少拍。续期条件同入场（前台在忙+簇负载≥
          down_fast_threshold），所以手指停顿再拖不会退出，松手后的
          fling 惯性动画也能续住；前台一停，最迟这么久后必回压缩路径。
    调大：滑动后高频保持更久、断续滑动更连贯，静态恢复慢、更费电；
    调小：松手沉底快更省电，但分段慢拖/惯性收尾可能提前松频。
    推荐：省电/标准 8（0.8秒）/ 性能 10 / 极速 15。范围 4~20。

 ─ 平滑与速度 ─────────────────────────────────────────────────────
  smoothing_up / smoothing_down   EMA 指数平滑系数（0~1）
    作用：新旧性能的融合比例，越大越跟手但越跳，越小越平稳但越迟钝。
    up 偏大（升频信新负载）、down 偏小（降频求稳）。
    推荐：up 0.50~0.85（性能档最大），down 0.20~0.45。
  headroom_factor   频率余量系数（≥1）
    作用：交互态算出目标后再乘的"安全余量"，1.30 = 多给 30% 性能防不够用。
    注意：仅交互态生效；非交互态余量恒为 1.0（省电不浪费）。
    调大滑动更稳但费电；调小更省电。推荐 1.15(省电)~1.45(性能)。
  headroom_ramp   旧版余量过渡带，现交互/非交互两条路径已不使用，
                  保留在配置里仅为兼容，无需修改。

 ─ 升降频确认（防抖）──────────────────────────────────────────────
  up_rate_limit_ticks / down_rate_limit_ticks
    作用：连续几个 tick 满足条件才真的升/降，数字越大越保守、越防抖
          （1 tick = 0.1秒）。交互态升频自动旁路确认、首拍直接到位，
          所以这里的确认拍数只影响非交互态。
    推荐：标准/性能升频 1，省电升频 2；降频 标准 2 / 省电 3 / 性能 4。

 ─ 快速通道（非线性修正，仅非交互态生效）─────────────────────────
  up_jump_threshold    利用率突增量超过它 → 直接大步升频
    推荐 0.30~0.35。（触摸滑动已由交互态接管，这里主要服务后台突发任务）
  slow_up_scale        滞回带内缓慢爬升的步长
    推荐 0.10(省电)~0.15(标准/性能)，过低（0.02）会有迟滞。
  slow_down_scale      滞回带内缓慢下降的步长
    调大降得快更省电，推荐 0.35~0.40。
  down_fast_threshold  双重身份：
    ① 非交互态利用率低于它 → 走"快速沉底"通道（×down_fast_mult 加速）；
    ② 交互态入场/续期的最低负载线（簇利用率高于它才可能进交互态）。
    设 0.30 = 30%以下判静态，约0.7秒沉底。
  down_fast_mult       非交互态快速沉底倍率，越大沉得越快（3.0~4.5）。
    交互态禁用（滑动中不允许猛降频）。
  spike_jump_threshold 非交互态单 tick 利用率突增超过它视为"尖峰毛刺"
  spike_decay          尖峰增量只保留这个比例（0=完全忽略，防瞬时毛刺拉频）
    推荐 threshold 0.30~0.35，decay 0.30~0.35。交互态旁路（触摸负载再尖
    也是真需求，不能衰减）。


【三、rules.yaml · FAS 游戏帧感知调度参数】（仅 FAS 应用生效）

  fas_enabled   FAS 全局开关
    false（默认）= 普通应用零探针零空转；只有 app_modes 里标 "fas"
                  的游戏进前台才唤醒 FAS（推荐，最省电）。
    true = 全局模式为 fas 时所有应用都可走 FAS。
  global_mode   日常模式：powersave/balance/performance/fast/fas
  app_modes     每个包名单独指定模式（游戏填 "fas"）

  fas_rules:
    fps_gears        全局可选帧率档（游戏实际渲染帧率动态匹配）
    fps_margin       帧率余量，帧稳在"目标+余量"以下就降频省电（帧）
    per_app_profiles 每个游戏单独的 target_fps / fps_margin

    cluster_profiles / auto_capacity_weight
      三簇算力权重，算法见第一部分。8Gen2 定制：1.00 / 2.43 / 2.69。
      权重越大：低 perf 时该簇越被压低频（省电），高 perf 时仍能拉满。
      中核/超大核权重加大 → 轻载游戏更愿意用小核、更省电；
      调小 → 更早动用大核、更稳帧但更费电。建议 ±0.2 以内微调。

    PID 控制器（帧率反馈调性能的快慢/过冲）：
      kp 0.05  比例项，越大帧率掉时补得越猛（太大频率抖动）
      ki 0.01  积分项，消除长期偏差（太大过冲）
      kd 0.006 微分项，压制变化速度（太大反应迟钝）

    perf_floor / perf_init / perf_ceil（FAS 专用，按频率表换算）
      8Gen2 定制：floor 0.30（≈小820/中1190/超大1425，游戏起步不卡）
                 init 0.50（≈小1162/中1651/超大1978），ceil 1.0
      floor 调高：最低帧更稳但更费电；调低更省电但复杂场景可能掉帧。
    perf_cold_boot 0.85   游戏冷启动头几秒的性能（防加载卡）
    freq_hysteresis 0.015 频率迟滞（比例），小于此变化不下发，防抖动

    loading_perf_floor/ceiling 0.60/0.70   加载条场景锁定的性能区间
    post_loading_perf 0.65                 加载完后的保护性能
    downgrade_boost_perf_inc 0.18          降档后发现掉帧的紧急提频量
    fast_decay_*                           连续稳帧时的快速降频步长（省电）
    （这些帧计数类参数与 SoC 无关，保持默认即可，不用按处理器换算）


【四、8Gen2 / 领先版 实测数据表（本包定值依据）】

  policy0  小核   cpu0-2   3×Cortex-A510      capacity 266
           307.2 ~ 2016 MHz（16 档）   权重 1.00
  policy3  中核   cpu3-6   2×A715 + 2×A710    capacity 811
           499.2 ~ 2803.2 MHz（19 档）权重 2.43
  policy7  超大核 cpu7     1×Cortex-X3        capacity 1024
           595.2 ~ 3360 MHz（20 档）  权重 2.69
  · 领先版(3.36GHz) 与标准版(3.2GHz) 的 capacity 表相同、调频机制相同，
    上述配置 AB/AC 步进通刷；标准版仅超大核最高档略低，perf 归一化后
    会自动落在各自真实最高频，无需改配置。

  日用实测效果（8Gen2 领先版真机，标准档；省电档同样验证）：
    桌面静态    小核 557~902（随后台真实负载）、中核 614、超大核 595
    滑动起步    触摸后 ≤0.2 秒中核由 614 拉到 2016~2458（首拍一步到位）
    快滑        中核中位 1536 / 峰值 2458，小核中位 1555
    慢拖        中核峰值 2803、超大核峰值 3187（重载时大核兜底）
    松手回落    前台渲染一停，约 1 秒退出交互态，5~9 秒内回到静态深底
    视频/小说   前台解码线程 util 0.10~0.15 < 闸门 0.25，走压缩低功耗路径
    丢帧率      设置页 2454 帧仅 1 帧 jank（0.04%）、0 次错过 vsync；
                省电档 2868 帧仅 1 帧 jank（0.03%）、0 次错过 vsync

【五、调参纪律（避免改坏）】
  · 一次只动 1~2 个参数，每个参数小幅调整（步长 0.05~0.10）后实测。
  · up_threshold 必须 > down_threshold；gain/系数注意给定的取值范围。
  · 省电与流畅主要靠"低地板 + 快沉底 + 够快的 slow_up_scale 回收"三者
    配合，不要单纯把 floor 抬高来换流畅——那正是要消灭的"悬频耗电"。
  · 改完保存即热生效；怀疑没生效就重启守护或重启手机。
